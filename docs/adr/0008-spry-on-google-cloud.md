# ADR 0008 — Spry on Google Cloud: a GCP service for every piece

## Context

Since Lab 7 Spry runs on AWS and is described in Terraform (`infra/`). Lab 9 asks what it would take
to run the same system on Google Cloud and what it would cost. Every AWS piece has a GCP
counterpart, but rarely an identical one. This ADR records the choice for each piece.

The configuration is in `gcp/`: a separate root module with its own HCP Terraform workspace
(`successfulsuccess-gcp`, execution mode Local), so one plan can never break both clouds.

> Submission route: I did not open a Google Cloud account (the free trial asked for a $30
> prepayment). `gcp/` passes `terraform init` and `terraform validate`; the app runs locally the way
> Cloud Run would run it (see `docs/lab9/`).

## Decision

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront + WAF, static frontend | Firebase Hosting | **Replace** | Free plan, CDN and certificate included. A rewrite of `/api/**` to Cloud Run gives one origin and no CORS, as CloudFront did. A bare Cloud Storage bucket would need a load balancer for HTTPS (billed per hour) |
| Lambda + function URL, FastAPI | Cloud Run | **Replace** | Same Docker image as locally, no Lambda adapter; only change: listen on `$PORT`. Min instances 0, request-based billing |
| ECR | Artifact Registry | **Replace** | Cleanup policy keeps the 3 newest images, inside the free 0.5 GB |
| Aurora Serverless v2 (0–1 ACU, pauses) | Cloud SQL for PostgreSQL `db-f1-micro`, 10 GB SSD | **Replace** | See *The database* below |
| — (Spry is on SQL, not DynamoDB) | Firestore | **Not used** | — |
| Cognito user pool + Google | Identity Platform | **Keep Cognito (for now)** | See *What stays on AWS* |
| EventBridge Scheduler | Cloud Scheduler | **Keep on AWS (for now)** | Part of the weekly report, a stretch goal |
| S3 event → Lambda (report) | Cloud Storage + Eventarc → Cloud Run | **Keep on AWS (for now)** | Same |
| SES | no Google service | **Keep SES** | See *E-mail* |
| Bedrock (agenda parser) | Vertex AI (Gemini, Claude in Model Garden) | **Keep on AWS (for now)** | See *What stays on AWS* |
| Secrets Manager / SSM | Secret Manager | **Replace** | The whole `DATABASE_URL` is one secret; the password is generated by Terraform and never written to Git |
| CloudWatch Logs | Cloud Logging | **Replace** | Automatic for Cloud Run, nothing to configure |
| IAM roles | Service accounts + IAM roles | **Replace** | One service account `spry-api` with only `cloudsql.client` and access to its one secret; not the default compute SA (Editor) |
| Terraform `aws` provider | Terraform `google` provider | **Replace** | Same HCL and workflow, a different state and workspace |

### The database

| Option | Latency | Bill (nobody using it) | Code |
|---|---|---|---|
| **Cloud SQL around the clock** | Best: same region as Cloud Run, Unix socket | ≈ $9.40 / month | No change: same PostgreSQL, same Alembic migrations |
| **Cloud SQL stopped at night** (`db_activation_policy = "NEVER"`) | Same while running; down while stopped | ≈ $1.70 stopped (disk only) + $0.0105 per running hour | No change, but someone has to start and stop it |
| Firestore | Good | $0 at student traffic (free quota every day) | Rewrite: no joins, no foreign keys, data access layer and migrations rewritten as documents |
| Keep Aurora on AWS, call it from Cloud Run | Worst: every query crosses clouds (europe-west1 ↔ eu-north-1, tens of ms per round trip) | Aurora stays ≈ $0.30, plus egress from GCP | No change, but needs a public Aurora endpoint or a VPN between clouds |

**Chosen: Cloud SQL, `db-f1-micro`, stopped between demos.** Spry is relational (meetings,
participants, users) and already has migrations; rewriting it for Firestore to save about $9 a month
is a bad trade for a course project. A cross-cloud database adds latency to every request and opens
the database to the internet. `db_activation_policy` is a Terraform variable, so stopping the
database is one `terraform apply`, not a console click.

### E-mail

Google Cloud has no e-mail service. **Keep SES** for the weekly report: a multicloud architecture is
allowed, and the report pipeline stays on AWS anyway. If the report moves to Cloud Scheduler +
Cloud Run, use **SendGrid** (free tier, HTTP API, no SMTP); its API key goes into **Secret Manager**
as `spry-sendgrid-api-key`, read by the `spry-api` service account only.

### What stays on AWS, and why

- **Sign-in (Cognito).** The users and their passwords live in the Cognito pool; Identity Platform
  cannot import Cognito password hashes, so moving means asking every user to sign up again. The
  Cloud Run API already verifies Cognito tokens (JWKS over HTTPS), so it works across clouds; the
  Firebase URL is added to the Cognito callback and logout URLs in `infra/terraform.tfvars`.
- **The agenda parser (Bedrock).** It works and its prompt is tuned for Claude on Bedrock. The same
  Claude models exist on Vertex AI, but the free-trial credit does not cover partner models.
- **The weekly report (EventBridge + Lambda + SES).** Stretch goal; not needed for the app to be
  usable.

## Consequences

- **Lock-in is in the managed services, not in compute.** The API image moved without code changes
  (one line: `--port ${PORT:-8000}`). What did not move is what is tied to a provider: user accounts
  (Cognito), the LLM API (Bedrock), e-mail (SES).
- **The bill changes shape.** On AWS the database pauses and an idle month costs ≈ $0.30. On GCP
  Cloud SQL does not pause, so an idle month costs ≈ $9.40 unless it is stopped. Cost table:
  `docs/lab9/cost-table.md`.
- **Two states, two workspaces.** `infra/` (AWS, remote execution) and `gcp/` (Google, local
  execution with `gcloud` credentials, no service account key). In CI the GCP side would use
  Workload Identity Federation, the same idea as dynamic credentials for AWS.
- **Clean up:** `terraform destroy` in `gcp/` removes everything; a stopped Cloud SQL instance still
  bills its disk.
